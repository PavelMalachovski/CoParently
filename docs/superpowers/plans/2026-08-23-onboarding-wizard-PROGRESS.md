Task 2 (`OnboardingState`): implemented at `23d50e6`. Seven JVM tests, one more than the plan
listed — a blank (whitespace) marker is treated as "not finished", which the plan's list did
not cover and the Firestore round-trip can produce.

Task 3 (steps, validation, persistence): implemented at `e58c8a2`, plus fixes at `9ae2d4b` and
`c1e68e3`. 13 JVM tests.

Task 3: DEVIATION from the plan's test #4. As written, `repeat(2) { viewModel.next() }` with a
blank name expected to land on `Child`, which contradicts test #2 in the same file — a blank
name blocks the profile step, so the second `next()` cannot advance. The test now names the
parent before advancing. The plan's *intent* (every step after the profile is skippable) is
unchanged and still asserted.

Task 3: DEVIATION — `OnboardingUiState` carries `isFinished` (the host's signal to leave) and
`canEditRelatives`, neither of which the plan's sketch listed. See the relatives note below.

Task 3: two defects found and fixed during self-review, both worth knowing about on the device
walk because they are the kind that look fine until walked:
  (a) `9ae2d4b` — Skip on the **last** step advanced blindly and, with nothing to advance to,
      did nothing at all. Next and Skip now share one exit that finishes the wizard.
  (b) `c1e68e3` — the profile step's save and `finish()`'s marker are two read-modify-writes
      against the same `users/{uid}` row. Interleaved, whichever wrote second dropped the
      other's field; losing the marker means the wizard reappears on the next launch over data
      already entered. One mutex now serializes every write the wizard makes.

Task 4 (screen and strings): implemented at `6c250df`. 22 keys × 5 locales, verified by grep
and by parsing every file as XML. The three data steps reuse `AllergyEditor`,
`MedicalProfileEditor`, `EmergencyContactEditor` and `DatePickerDialog` — no new field editor
was written.

Task 4: DEVIATION — one key beyond the plan's 21, `onboarding_relatives_needs_child`. Emergency
contacts belong to a **child** record, so a parent who skipped the child step has nowhere
honest to put one. The step now says so and hides the editor, rather than collecting contacts
the save would silently drop. This is a step precondition, not a missing editor, so it did not
meet the plan's "stop and ask" bar — but it is a product decision and is cheap to flip.

Task 5 (start destination): implemented at `1329250`. The decision lives in `AuthStateViewModel`
beside the authentication state, exposed as `needsOnboarding: StateFlow<Boolean?>`; null routes
to `Loading`, never to `Home`.

Task 5: SCOPE ADDITION the plan did not name. `AuthScreen`'s `onAuthSuccess` navigated straight
to `Home`, so the routing decision only ever ran on a cold start and a parent who signed up in
that very session would never have seen the wizard. It now parks on `Loading` and lets the same
single decision resolve. Worth re-reading if the device walk shows anything odd right after
sign-up.

Task 5: the decision **waits** for the account's Room row (bounded, 5 s, the value
`ProfileViewModel` uses) rather than reading once, because `ensureProfile` writes that row
asynchronously and a read that lands first reports "no user" — which the predicate reads as
"nobody to ask". A timeout falls back to *not* asking.

Task 6 (verification and the device walk): NOT STARTED. See the constraint at the top.

## What the four start states do, reasoned through (Task 5, Step 3 — reasoned, not observed)

| State | Route |
|---|---|
| Signed out | `isAuthenticated != true` → `Auth`. |
| Signed in, answer not yet known | `isLoading`, or `needsOnboarding == null` → `Loading`. |
| Signed in, needs onboarding | `Onboarding`. Not in `BottomNavDestination.topLevelRoutes`, so the bottom bar hides itself. |
| Signed in, does not need it | `Home`, unchanged. |
