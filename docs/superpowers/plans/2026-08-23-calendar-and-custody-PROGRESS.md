  the proxy allows. The eleven new `dayOverrides` cases were watched fail before the rule existed

  `ChangeRequestHighlight`, `CustodyChangeAnnouncement`, `CustodyProposalTransition`, `CustodyKey`

## Ledger

Task 1 (`DayOverride`, transitions): `9acbe93`. 7 tests, verified passing.

Task 2 (`CustodyResolver`, `HandoverCalculator`): `12a8f2b`. 13 new tests including the two the
plan flagged as the ones that would otherwise ship broken — a swap creating a handover, and a swap
removing the one it displaced.

Task 3 (storage and sync): `109ab58`. Room 15 → 16, one nullable column. **Two problems the plan
did not name, both found by reading the write path rather than by a test:**
  (a) `setCustody` replaces the whole document and `pushToFirestore` rebuilt the object from
      scratch, so **any pattern save would have deleted every agreed swap** — including
      `republish`, which runs during ordinary mirroring with no user action behind it. It now
      carries them across, the way it already carried `createdAt`.
  (b) `firestore.rules` requires every update to stamp `lastModifiedBy` with its caller, and that
      is exactly the field `CustodyChangeAnnouncement` reads to decide whether the *pattern*
      changed. So **every swap would have raised the co-parent's "the schedule changed" banner**
      about a day nobody had agreed to. The document now records `lastModifiedKind`
      (PATTERN | SWAP), defaulting to PATTERN — the honest default for documents written before it
      existed.

Task 3: NOT DONE — `app/schemas/…/16.json` is generated by Room at build time and is absent from
the commit, as is B2's `15.json`. The first local `assembleDebug` produces both; **commit them**,
or the instrumented migration tests have no schema to validate against.

Task 4 (rules): `20f35ef`. 11 emulator cases. Beyond the plan's four, two more guards, both found
while writing the first:
  - a **pattern rewrite riding along on a write stamped `SWAP`** — the banner is suppressed for
    that stamp, so without an only-the-swap clause it becomes a way to replace the co-parent's
    schedule in total silence;
  - a **create that bakes in an already-accepted swap**, the same hole `noForeignMarksOnCreate`
    closes for conversations.
  `lastModifiedAt` is outside the allowed set, which is what stops a swap re-dating the document.

Task 4: DESIGN NOTE. Rules cannot iterate a map, so a swap write names the one date it touches in
`lastSwapDate` and the rule requires the diff to affect only that key — a lie is then
self-defeating. That field is new and is on the document, not in Room.

Task 4: DECISION worth a second opinion. A **re-offer may replace an already-ACCEPTED swap**.
Renegotiating an agreed day has to be possible and it is not silent — the other parent sees the
request in their inbox and the arrows on that date — but the day does revert to the pattern while
the new offer is pending. Flipping it is one clause in `validDayOverrideAt` and one line in
`DayOverrideTransition.offer`.

Task 5 (remove the banner): `2d8091a`. Also removed `CalendarViewModel.nextHandover`, which had no
other consumer and would have been computing handovers without swaps. Deleted five string keys and
one plurals block from all five locales, each checked for other references first;

Task 6 (diagonal and arrows): `55e5518`. DayCellFillsTest 10 → 16.
  - The diagonal **replaces** the full-hue left edge that marked the first day of a custody run.
    Both answered "the child changes hands here"; keeping both would be the two-answers-to-one-

  - Two `drawPath` calls, not a gradient: a gradient smears a boundary that is not gradual. The
    first repaints the triangle with the opaque base, because two translucent parent hues stacked
    read as a muddy third colour rather than as the previous parent.
  - DEVIATION: the diagonal is **month-grid only**. The plan lists `DayWeekView`, but the week view

    over. Pending-swap arrows are likewise month-grid only, where the swap can be offered. **A
    parent working only in week view will not see a pending swap on the grid**; the inbox still
    shows it.

Task 7 (long-press sheet and inbox): `ab4e2de`. The swap section renders **above** the two existing

## Two things to watch on the devices

1. **The banner.** Offer and answer a swap on phone A and confirm phone B raises *no* "custody
   schedule changed" banner, and that a genuine pattern change right afterwards still does. That
   is `lastModifiedKind` doing its job, and it is the change most likely to be subtly wrong.
2. **A pattern save after an agreed swap.** Agree a swap, then edit the custody pattern from
   Settings, and confirm the swap survives on both phones. That is the carry-over in
   `pushToFirestore`; before it, the swap would have vanished with no error anywhere.
